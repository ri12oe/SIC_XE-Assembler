# SIC/XE Assembler Project Plan

## 1. Project goal

Build a two-pass assembler that reads SIC/XE assembly-language source files and produces:

- An object program containing header (`H`), text (`T`), modification (`M`), and end (`E`) records.
- A human-readable assembly listing with addresses, source statements, generated object code, and errors.
- Symbol-table and literal-table reports for debugging and demonstration.

**Recommended language:** Java 17. Java provides portable file handling, strong data modeling, testing support, and straightforward command-line execution. The design can be implemented in C++ instead if the course requires it; only the syntax and build commands should change.

## 2. Scope and success criteria

### Required SIC/XE support

1. Source-line fields: optional label, operation, operand, comments, and blank lines.
2. Directives: `START`, `END`, `BYTE`, `WORD`, `RESB`, `RESW`, `BASE`, `NOBASE`, `LTORG`, and `EQU`.
3. Symbol definitions and forward references.
4. Literal operands such as `=C'EOF'` and `=X'F1'`.
5. Instruction formats 1, 2, 3, and 4.
6. Addressing modes: simple, immediate (`#`), indirect (`@`), indexed (`,X`), PC-relative, base-relative, and extended (`+`) format.
7. Object-program records, including modification records for relocatable format-4 addresses.
8. Clear errors for invalid opcodes, duplicate/undefined symbols, malformed constants, invalid registers, range errors, and bad addressing combinations.

### Completion definition

The project is complete when all six test programs generate expected addresses and object code, valid object records, understandable listing/error output, and a short user guide explaining how to build and run the assembler.

## 3. Proposed design

### Command-line interface

```text
java -jar sicxe-assembler.jar input.asm --out output/
```

The output directory should contain:

```text
input.obj       SIC/XE object program
input.lst       Source, addresses, object code, and diagnostics
input.sym       Sorted symbol table
input.lit       Literal table
input.int       Pass-1 intermediate representation (debugging aid)
```

### Module layout

```text
src/

  parser/
    SourceParser.java               Parses source into SourceLine objects
    OperandParser.java              Parses addressing prefixes, index suffix, literals
  model/

    IntermediateLine.java           Pass-1 address, block, and source information
    Symbol.java
    Literal.java
    Instruction.java
    ObjectProgram.java
  tables/

    RegisterTable.java
    SymbolTable.java
    LiteralTable.java
  pass/
    PassOne.java                    Addresses, symbols, literals, intermediate output
    PassTwo.java                    Object code and object-record generation
  output/
    ListingWriter.java
    ObjectWriter.java
    ReportWriter.java
  diagnostics/
```

### Core data

| Structure | Essential contents |
| --- | --- |
| Opcode table | mnemonic, opcode byte, permitted formats |
| Symbol table | name, address/value, relocatable/absolute flag, defined line |
| Literal table | literal spelling, bytes, assigned address, emitted status |
| Intermediate line | original source, parsed fields, address, generated bytes, diagnostics |
| Text-record builder | start address, accumulated bytes, 30-byte maximum |

## 4. Assembly workflow

### Pass 1: analyze and assign addresses

1. Read each source line and retain its original text and line number.
2. Parse label, opcode, operand, and comment; report syntax errors without aborting the whole run.
3. Initialize the location counter from `START`; otherwise start at zero.
4. Validate instructions/directives and compute each statement's byte size.
5. Add labels to the symbol table, detecting duplicates.
6. Collect literals when operands use `=...`; allocate pending literals at `LTORG` and `END`.
7. Write each resolved statement to the intermediate representation.
8. Determine program name, start address, execution address, and total length.

### Pass 2: encode and emit records

1. Read the intermediate representation and resolved symbol/literal tables.
2. Encode directive constants (`BYTE` and `WORD`).
3. Encode instruction formats:
   - Format 1: opcode only.
   - Format 2: opcode plus validated register/numeric fields.
   - Formats 3/4: set `n i x b p e` flags, calculate displacement/address, and detect overflow.
4. Use PC-relative addressing when possible; otherwise use configured base-relative addressing; require format 4 when neither fits.
5. Build text records, splitting them at reservation statements, literal pools, address gaps, and the 30-byte record limit.
6. Emit modification records for relocatable fields that need loader adjustment.
7. Write `H`, `T`, `M`, and `E` records, then produce the listing and reports.

## 5. Test plan: six assembly programs

Each test should have checked-in source, expected object program, and expected key listing/symbol-table values.

| # | Program purpose | Features verified |
| --- | --- | --- |
| 1 | Minimal `START`/`END` program | Header/end records, format 3, simple symbol |
| 2 | Data-definition program | `BYTE` character/hex constants, `WORD`, `RESB`, `RESW`, text-record breaks |
| 3 | Addressing-modes program | Simple, immediate, indirect, indexed, PC-relative displacement |
| 4 | Base and extended program | `BASE`, `NOBASE`, base-relative encoding, format 4, modification records |
| 5 | Literals and forward references | `LTORG`, `=C`, `=X`, literal placement, unresolved-then-resolved symbols |
| 6 | Error-handling program | Invalid opcode/register, duplicate label, undefined symbol, malformed constant, displacement overflow |

For tests 1-5, compare generated `.obj` files exactly against expected files. For test 6, compare expected diagnostic codes/messages and confirm no invalid object code is silently emitted. Add focused unit tests for parsing, numeric/hex conversion, each instruction format, and text-record splitting.


### Baseline test programs

Because official test programs have not been provided, the project will use temporary local smoke tests during early development:

- `tests/programs/minimal.asm` - primary parser and Pass 1 smoke test
- `tests/programs/comments.asm` - comments and blank-line parsing
- `tests/programs/instructions.asm` - opcode and register table validation

Official six-program testing is deferred until sample programs or instructor requirements are provided.

Use the following ownership for a four-person team. For a smaller team, combine adjacent roles while preserving the listed interfaces and review points.

| Role | Primary responsibility | Milestone contribution |
| --- | --- | --- |
| Member A: coordinator/parser | Requirements, opcode/register data, parser, CLI, diagnostics contract | Sep 14-Oct 4; coordinates integration |
| Member B: Pass 1 | Location management, directives, symbol/literal tables, intermediate representation | Oct 5-18 |
| Member C: Pass 2 | Instruction encoder, addressing calculations, relocation/modification records | Oct 19-Nov 1 |
| Member D: output/quality | Object/listing/report writers, expected outputs, automated tests, documentation/demo | Continuous; leads Nov 2-Dec |

### Shared responsibilities

1. Hold one short weekly integration meeting and merge only after running the six-program suite.
2. Review another member's code before integration, especially interfaces between parser, Pass 1, and Pass 2.
3. Keep a defect list with source line, expected behavior, actual behavior, owner, and resolution.
4. Every member explains one test program and one assembler component in the final demonstration.

## 8. Weekly working routine

1. **Monday:** choose the week's deliverable and assign concrete tasks.
2. **Midweek:** integrate partial work; run the current automated tests; record defects.
3. **Friday/Sunday:** demonstrate the milestone output, update documentation, and re-plan the following week.

Maintain a small issue board with `To do`, `In progress`, `Review`, and `Done` columns. No feature should enter `Done` until a representative assembly program and expected output cover it.

## 9. Risks and mitigations

| Risk | Mitigation |
| --- | --- |
| Format-3 displacement mistakes | Unit-test positive/negative PC-relative offsets and base-relative fallback independently. |
| Invalid object-record boundaries | Centralize text-record construction and test 30-byte, gap, and reservation boundaries. |
| Team integration conflicts | Define `SourceLine`, `IntermediateLine`, and diagnostic interfaces before Pass 1 starts. |
| Late discovery of missing features | Draft all six programs during design week and use them as the implementation checklist. |
| Schedule slip | Keep November 30 onward free of new features; prioritize correct core assembly over optional enhancements. |
